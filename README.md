# 知条件 · AI 选股产品 - 自然语言选股与策略解释器

此产品希望把用户想筛选“公司经营不错、估值别太贵”这样个股的模糊想法，经过AI意图识别，具象成标准化、可修改的选股量化条件。并且，此产品面向需要反复筛选 A 股的投资者，支持基本面筛选、波段筛选及两者条件的交集个股呈现，用真实数据说明入选和排除原因，方便继续比较与核验。

此产品不替用户做买卖决定，仅供参考。

## 一、怎么用

### 1）选择研究方向

进入工作台后，选择「价值与基本面」「波段」或「两者交集」。作为 MVP，暂选 50 只 A 股作为 Demo 范围，覆盖传统行业和科技题材；页面会加载这些股票的官方数据，并显示进度。

### 2）选定关注范围

在「板块范围」选择行业或题材，也可以保持不限。例如：同时选中半导体、PCB，则表示两类股票均被展示，而非一家公司同时属于两个类别。

### 3）说出条件，或直接修改参数

例如输入“PE上限设为20”“只看半导体或PCB”。如果输入“更稳一点”，系统会先确认用户希望表达的是股价波动较小，还是公司财务负担较轻。

### 4）核对修改，再确认筛选

解析后会显示修改前后的对比和预计入选数量。点击「确认并筛选」，下方条件与结果一起更新，改动处会高亮；若直接手动调整参数，则点击「执行筛选」。

### 5）看清为什么入选或排除

切换「入选」「排除」「数据不足 / 不适用」或「仅差一项」，查看哪些条件满足、哪些不满足。点击股票名称，可核对实际数值、统计日期、公式、走势和原始数据回执。

### 6）继续比较和研究

最多选择三家公司并排比较，也可以把策略保存到当前浏览器，或导出结果、条件和执行记录。需要核验单只股票时，可在详情中重新查询扶摇证据；查询不会自动覆盖当前结果。

## 二、两套选股模型的介绍与区别

这个 MVP 选择做一个可以直接操作的选股工作台：用户用自然语言提出要求，核对具体条件后，再查看真实数据筛出的股票。演示范围先限定为 50 只个股，优先把条件修改、结果解释和证据核验做完整。

### 1、价值与基本面筛选

侧重关注“公司经营质量如何，当前定价是否符合自己的要求”。覆盖营收与利润增长、ROE、负债水平、现金流质量及 PE/PB/PS，并结合 MA20/60 等中期价格特征。聚焦于企业经营、估值与中期状态，适合建立研究候选池；与波段模型相比，不把短期量价变化作为主要筛选依据。

### 2、波段筛选

侧重关注“近期价格、成交量与波动是否形成值得研究的组合”。面向约 3–7 个交易日的研究窗口，覆盖 MA5/10 方向与距离、近期上穿、平台突破、回撤整理、相对成交量、ATR/RSI 和机构席位披露。

聚焦于短周期强弱、位置和波动风险，不能用来替代基本面判断，也不代表预测持有几天即可盈利。

### 3、两者交集

同时满足公司层面与短周期量价要求。两套条件独立保留、分别修改；选择交集后，同一只股票必须同时通过两组条件。分开设置是为了让不同研究目标使用不同时间尺度，避免把财务质量和短期信号混成一个难以解释的总分。模板是可修改的起点，阈值没有经过收益回测优化。

## 三、AI 与工程化

### 1、各部分负责什么

#### 1）DeepSeek deepseek-v4-pro

在输入框栏，把复杂自然语言转成结构化条件；提出澄清问题，解释假设与修改。解析 API：app/api/interpret/route.ts

#### 2）本地意图解析器

负责处理明确的指标、上下限、区间、板块、模板及部分多轮追问，减少不必要的模型调用。意图解析：lib/intent.ts

#### 3）规则与筛选引擎

负责校验方案、计算每只股票是否满足条件，最后生成入选／排除／未知的逐项解释。筛选引擎：lib/screener.ts

#### 4）金融数据适配层

负责获取授权数据，包括检查接口状态、字段和时间，再计算派生指标。扶摇适配器：lib/providers/fuyao.ts、数据组装：lib/official-data.ts

#### 5）工作台

负责展示修改前后差异、请求确认、同步条件与结果，提供比较、保存和证据核验。工作台：app/page.tsx、确认校验与差异：lib/plan-feedback.ts

DeepSeek 不生成股票的实际财务或行情数值，不直接决定入选名单，也不自行下单。同一份数据、同一套条件由同一段代码执行，得到相同结果。

开发过程中使用 Codex 辅助实现、测试和排障；产品内的模型调用与开发用 AI 分开记录，详见 [AI 使用与验证记录](docs/AI_LOG.md)。

### 2、如何理解用户输入

解析时，系统会同时读取用户输入、当前条件、选股方式、最近对话和可用指标。明确表达由本地规则处理，复杂表达交给 DeepSeek。

解析结果分为三种：需要补充信息、已有可确认的方案、当前不支持。方案通过代码检查后，页面展示修改前后对比和预计名单变化；用户确认后，才更新条件与结果。

#### 3、识别指标与修改意图

本地字典将“市盈率”“PE”等别名映射到同一字段，区分新增、删除、修改上限、修改下限和设置区间。只修改明确提到的条件，保留其他条件；不能只解析一句话中的一半，却把整句话标记为成功。

#### 1）先澄清含糊表达

“更稳”会区分价格波动与财务负担；“机构活跃度”会要求明确可验证的上榜天数口径。“放宽一点”提出具体幅度供用户确认，不直接改参数。多轮处理中保留原句中的其他要求，避免澄清一个指标时丢掉已说过的板块或范围。

#### 2）提供给模型的信息

服务端提供当前指标字典、单位、分组、行业与题材目录、当前方案和简短历史。最近最多保留 8 条对话消息，模型侧历史压缩为摘要、问题和假设。模型使用低温度 0.1、JSON 输出格式与 3000 输出 token 上限，单次调用最多等待 45 秒。

#### 3）检查返回的规则

每条数值条件使用 field / op / value，运算符只允许 >、>=、<、<=；每组最多 24 条，字段分组正确、数值有限、编号不重复。模型不能创造字典外指标。结构不合法的回答不会进入编辑区。

### 4、如何检查解析结果

#### 1）范围和条件分开计算

行业／题材多选是“满足其中任一个”；所选数值条件是“全部满足”。交集视图再合并基本面与波段两组条件。数值条件之间的任意 OR 组合目前不支持，不能自动改成 AND。

#### 2）区分冲突、重复和偏好取舍

PE ≥ 80 与 PE ≤ 30 属于不可执行的冲突；PE ≤ 30 已覆盖 PE ≤ 50，会提示移除重复条件；“低估值且高增长”只是可能收窄样本，不会被当作逻辑错误或自动放宽。两组条件都会检查，不能因冲突位于另一视图而漏过。

#### 3）检查指标的有效范围

例如 RSI 为 0–100、近 5 日机构上榜天数为 0–5。无法满足的边界会被拦截。非正 PE/PB 不按普通正值估值比较，亏损时也不强行计算正盈利口径的现金利润比。

#### 4）对关键语义增加独立校验

“半导体或 PCB”不能被改写成同时属于两者；“站上五日均线”要求距 MA5 大于 0，不能混同于“大于等于 0”。真实验证中曾发现模型错译均线边界，现由代码拦截并提示重述。这是特定场景的保护，不等于证明所有自然语言都能正确理解。

#### 5）确认时再次检查

提案带有生成时的规则版本指纹；如果用户已经改过条件，旧提案不能直接确认。确认入口还会检查方案结构、空条件组及冲突，再把同一份新方案同时写入编辑区和执行状态，避免界面看起来变了、结果仍沿用旧规则。

#### 6）没有改动也给出解释

相同条件不重复添加；入选数量不变，会显示已经重新执行。修改了另一套模型时，会提示切换视图查看。每次执行保留规则版本、数据版本、时间、覆盖率及关联的 AI 请求编号，当前会话最多保留 20 次，可随结果导出。

### 5、MCP 与 API 如何使用

当前生产主链路使用扶摇 REST API，由服务端携带 X-api-key 读取日线、报价、估值、财报和机构披露。模型提出条件后，由固定代码调用数据接口与筛选引擎；没有让模型自由拼接接口、选择任意来源或执行任意工具。

仓库另保留 iFinD MCP 适配器：通过 HTTP JSON-RPC 完成 initialize、notifications/initialized，再以 tools/call 调用 get_stock_financials；处理会话 ID、JSON 或 SSE 响应及工具错误，原样保留证据。

它曾在本地查询成功，但生产环境出现 522 超时，因此当前演示界面和筛选主链路不依赖 iFinD，其可用性仍需进一步排查。

### 6、数据检查和异常处理

系统会记录数据来源、检查字段并保留计算公式。上游数据也可能有误，因此不能承诺数字永远准确；查不到或校验失败时，会直接说明原因。

#### 1）供应商返回 HTTP 200，但业务状态失败

继续检查扶摇响应中的业务码和数据体；失败时抛出明确错误，不把 HTTP 成功当作数据成功。

#### 2）网络超时、限流或部分临时服务错误

扶摇单次请求超时 20 秒；最多请求 3 次，重试间隔为 0.5 秒、1 秒。鉴权等不可重试错误直接失败。

#### 3）全量加载压力

股票加载使用 2 个并发任务；市场上下文短期缓存约 60 秒，单股结果约 5 分钟。失败缓存会移除，允许重试；不同服务实例不共享缓存。

#### 4）日期、字段或日线异常

检查证券代码、财报期次、币种及披露时间；日线检查有限数值、重复日期、价格高低关系、非负成交量与金额等。

#### 5）个别股票或字段缺失

保留未知值，不填 0、不借用旧公开快照。已知条件不满足时归入“排除”，同时保留缺失项；没有已知失败但仍缺数据时归入“数据不足 / 不适用”。

#### 6）初始化或刷新失败

已有官方数据时保留其原时间；首次没有数据则显示加载失败。不会把旧数据标记为刚更新。

#### 7）机构披露不完整

最近 20 个交易日完整取得后才生成对应的 5 日／20 日计数，不把漏取某天当作当天未上榜。

#### 8）模型超时、格式错误或语义校验失败

保留原条件和结果，明确显示未更新；支持取消客户端等待。取消不保证已发出的上游推理立即停止。

#### 9）零结果

如实显示 0 只，保留排除依据与“仅差一项”入口，不擅自放宽条件凑出股票。

#### 10）超范围要求与合规边界

已下架指标、缺少必要历史数据的连续季度要求不生成替代条件；对收益保证、内幕、操纵等明确表达做拒绝处理，模型协议同时禁止确定性涨跌预测和直接买卖建议。

服务端还限制输入长度（用户描述最多 800 字符、请求体最多 26,000 字符）、校验历史与模型输出结构。密钥仅从服务端环境读取，前端不包含密钥；授权原始回执不放入公开源码或静态构建资源。

部署在 Sites 的 Worker 环境，冷启动回归测试防止模块初始化时出现生产环境禁止的随机值或网络操作。

## 四、数据与时间：页面上的数字从哪里来

产品运行时的金融数值来自扶摇授权接口，衍生指标由代码计算。东方财富、腾讯等旧公开快照不再作为产品数据或失败时的替代来源。

### 1、股票名称、代码、行业和题材

50 只人工选取的 Demo 股票；题材依据公司业务材料整理，详情提供相关来源链接。行业与题材是分类，不代表实时热点或龙头排名。

### 2、最新报价、PE/PB/PS

扶摇报价快照与估值快照，保留供应商给出的批次时间

### 3、营收、利润、现金流、ROE、负债率

扶摇利润表、现金流量表及财务指标；按公司选择截至筛选日已经披露的最新报告期。

### 4、增长率与现金利润比

同期财务字段计算同比；经营现金流净额除以同报告期的合并净利润，后者必须大于 0。归母利润同比用上年同期绝对值作分母，不能把扭亏与持续增长混为一谈。

### 5、均线、上穿、涨跌幅、回撤、量能、ATR/RSI

扶摇前复权日线，由代码统一计算，字段字典给出单位与公式；前复权价格用于研究走势，不是下单报价。

### 6、机构上榜天数

扶摇龙虎榜机构席位披露，按完整交易日集合统计；0 表示没有查到对应上榜记录，不代表没有机构交易。

### 7、原始证据

随数据保留接口地址、抓取时间、请求编号和回执；股票详情可查看来源或下载本次数据的授权回执。

### 8、避免多种时间混淆

日线条件使用最近一个已完整收盘且上游有数据的交易日，上海时间 15:30 前保守地不使用当天日线；最新报价与估值可能属于另一个时间批次。财报的“报告期”是数据覆盖到哪一天，“披露日”是市场何时能看到它，“抓取时间”则是本次请求取得它的时间。

页面分别保留这些信息，不把供应商批次时间当作每只股票逐笔更新的时间。

### 9、统一财务口径

半年报的累计收入、现金流和 ROE 不能直接当成全年数据；同比尽量比较上年同一报告期，缺少可比项则保留未知。打开页面或点击刷新会取最新可用数据，短期缓存减少重复请求；这不是持续推送的逐笔行情。财报及前复权历史可能修订，因此当前数据不能直接拿来宣称严格的历史时点回测。

## 五、本地启动与验证

### 1、安装依赖

使用 Node.js 24 和 npm。下载仓库后，在项目目录执行：

```sh
npm ci
cp .env.example .env.local
```

### 2、配置环境变量

在 .env.local 填入自己的授权配置，不要提交这个文件：

#### 1）HITHINK_FINANCE_API_KEY

扶摇金融数据授权。加载真实股票数据必需

#### 2）LLM_BASE_URL

模型接口地址，默认 https://api.deepseek.com。使用 DeepSeek 时必需

#### 3）LLM_MODEL

模型名，默认 deepseek-v4-pro。使用 DeepSeek 时必需。

#### 4）LLM_API_KEY

模型调用授权。复杂自由表达解析必需；明确语法仍可本地解析

#### 5）IFIND_API_TOKEN

保留的 iFinD MCP 适配器授权。可选，当前演示主链路不依赖它。

### 2、启动服务

显式载入环境文件并启动：

```sh
node --env-file=.env.local scripts/run-framework.mjs dev
```

默认本地地址为 http://localhost:5173，具体以启动日志为准。.env.local 属于本地配置；线上部署需单独设置服务端环境变量。

### 3、运行验证

```sh
node --experimental-strip-types --test tests/*.test.ts tests/*.test.mjs
npx tsc --noEmit
npm run build
```

运行真实接口验证时，先启动已配置密钥的本地服务，并用 mkdir -p work 创建输出目录，再执行 node --experimental-strip-types scripts/verify-v5.ts 或 node scripts/check-v5-workflow.mjs。

这会使用供应商额度；细粒度回执写入被 Git 忽略的 work/，不上传公开仓库。tests/fixtures 的旧公开数据只用于回归测试，不会作为网站数据加载。


## 六、已知边界与下一步计划

### 1、当前使用边界

当前演示范围为 50 只 A 股，结果表示符合所设条件，不是全市场排名或收益预测；策略模板尚未经过收益回测验证。

筛选使用完整收盘日数据，报价、估值和财报各自保留时间。接口或字段缺失时显示失败或未知，不用估算值补齐。策略保存在当前浏览器，暂不跨设备同步。

### 2、下一步计划补充的筛选条件（尚未实现）

#### 1）机构集中度

计划增加机构集中度的区间筛选。先明确采用机构持仓占比还是持仓分布集中程度，再核验数据来源、统计分母与披露日期，让用户知道这个指标具体衡量什么。当前的机构席位上榜记录不能直接替代机构持仓数据。

#### 2）龙虎榜上榜次数

计划扩展龙虎榜上榜次数筛选，支持选择统计窗口，并明确同一天因多个原因上榜、单日榜与三日榜重叠时如何去重。

目前已实现的是近 5 日、近 20 日“机构席位上榜天数”，统计有机构席位披露的交易日数量；下一步希望补充的是更完整的龙虎榜上榜次数口径，两者不混用。

#### 3）筹码集中价位估算

计划加入筹码集中价位的估算，以及现价与估算集中区间距离等筛选条件。实施前需确定可用的成交与换手数据、估算方法和验证方式，并展示计算假设与误差范围。这类结果会明确标为估算，不当作真实账户持仓成本。

这三类条件目前均未作为上述新增能力上线。后续会先完成数据接入、口径核验和测试，再加入手动筛选与自然语言解析。
